`POST /api/v1/accounts` accepts a JSON object containing `accountNumber` (required,
nonblank, at most 64 characters) and `currency` (optional; defaults to `USD`, the
only supported currency). Account numbers retain their exact spelling and must
be unique. Existing V1–V5 have no account-holder name or email columns, so these
fields are not accepted.

Example request:

```json
{"accountNumber":"BANKOPS-0001","currency":"USD"}
```

A successful request returns HTTP 201 with `id`, `accountNumber`, `currency`,
`balance`, and `createdAt`. IDs are generated by the server, timestamps by
PostgreSQL, and both stored balances start at zero. Any unknown request field,
including `id`, `balance`, or `openingBalance`, is rejected with HTTP 400.

Validation failures return 400 with field messages. Duplicate account numbers
return 409. Database integrity failures return 500; database or transaction
availability failures return 503. Responses never include SQL or database error
details. The service transaction commits before a 201 response is returned.

Tests require `BANKOPS_TEST_DB_URL`, `BANKOPS_TEST_DB_USER`, and
`BANKOPS_TEST_DB_PASSWORD` pointing to disposable PostgreSQL. They create random
isolated schemas; run `mvnw.cmd test` with those variables set. API tests send
real HTTP requests to a random server port and check committed PostgreSQL rows.

`GET /api/v1/accounts/{accountId}` accepts a UUID and returns HTTP 200 with the
same public account representation (`id`, `accountNumber`, `currency`, `balance`,
and `createdAt`). It uses a read-only transaction and returns committed balances;
it does not expose the internal opening balance or ledger rows. Unknown accounts
return 404 with `ACCOUNT_NOT_FOUND`; malformed UUIDs return 400 with
`INVALID_ACCOUNT_ID`. Database failures use safe responses without SQL details.

`GET /api/v1/accounts/{accountId}/transactions?page=0&size=20` returns completed
transfer history from that account's immutable ledger postings. CREDIT postings
are `INCOMING`; DEBIT postings are `OUTGOING`. Each item contains `transferId`,
posting `timestamp`, `direction`, positive `amount`, `currency`, and `status`.
PENDING and FAILED transfers are excluded. No ledger IDs, keys, fingerprints,
account balances, or other internal fields are returned.

The response contains `transactions`, zero-based `page`, `size`, `totalElements`,
and `totalPages`. Page must be nonnegative; size defaults to 20 and must be 1–100.
Results sort by posting timestamp descending, then transfer UUID descending for
stable ties. Pages beyond the last return an empty list with the same totals.
The count and entries use one read-only repeatable-read transaction; separate
page requests may observe newer committed transfers. Existing accounts without
history return 200 with an empty page; unknown accounts return 404. Malformed UUIDs
or pagination values return safe 400 responses.
